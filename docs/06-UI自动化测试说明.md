# 06 UI 自动化测试说明（Selenium）

| 项目 | 内容 |
|---|---|
| 文档编号 | BS-TEST-DOC-06 |
| 被测系统 | BlogSystem 博客系统 v0.0.1（前端静态页面） |
| 技术栈 | Java + Selenium WebDriver 4.x + JUnit5 + Spring Boot Test |
| 用例数 | 33 条（全部通过） |
| 编写日期 | 2026-08 |

## 1. 框架设计

```
src/test/java/org/example/blogsystem/ui/
└── BlogUiTest.java          # UI 自动化测试主类（33 条用例）

tests/evidence/ui/           # 截图证据（34 张，随用例执行本地生成；UI-19 拆为回显/保存两步；该目录不入库）
```

| 设计要点 | 说明 |
|---|---|
| `@SpringBootTest(RANDOM_PORT)` | 测试自己启动应用并分配随机端口，无需手工启动 8080，可进 CI |
| `@ActiveProfiles("test")` | 使用独立测试数据库配置，与开发/生产隔离 |
| Headless Chrome | `--headless=new` 无界面运行，执行快、适合 CI |
| 显式等待（WebDriverWait） | 全部使用显式等待元素/URL/alert，不使用 `Thread.sleep`，降低偶发失败 |
| 截图断言 | 每用例关键步骤截图到 `tests/evidence/ui/`，并断言"文件生成且非空" |
| 样式断言 | 除"元素存在"外，还断言关键元素的**计算样式**（背景非透明、内边距/圆角非 0），避免"元素都在、样式全丢"的假通过（对应 BUG-18） |
| 弹框文本证据 | 原生 alert/confirm 无法被截图捕获（见第 2 节），额外产出 `alert-evidence.md` 文本证据 |
| 数据独立 | 每次注册随机用户名（前缀 + 时间戳），用例可重复执行、互不污染 |
| 登录态隔离 | `@BeforeEach` 回到登录页并 `sessionStorage.clear()`，保证用例从干净状态开始 |

## 2. 关键技术点与踩坑记录

| 问题 | 现象 | 解决方案 |
|---|---|---|
| editor.md 编辑器内容写入 | `window.editor.setMarkdown()` 报 `Cannot read properties of undefined (reading 'setValue')` | editor.md 异步挂载底层 CodeMirror，改为等待 `window.editor.cm.setValue` 就绪后直接调 `cm.setValue()` |
| 原生 alert 阻塞 | 登录失败/发表成功等提示为 `alert()`，不处理会阻塞后续操作 | 封装 `acceptAlert(scene)`：显式等待 `alertIsPresent()` → 取文本 → `accept()` |
| **原生弹框无法截图** | 截图里只有页面、看不到"究竟提示了什么"（alert 不属于页面 DOM） | 关闭弹窗后，用 JS 把**实际提示文本**绘制成右上角黄色浮层再截图；同时把文本累积落盘为 `alert-evidence.md` |
| 删除确认弹窗 | 删除博客前有 `confirm()` | 同样用 `acceptAlert()` 处理，再等待跳转回列表页 |
| 页面跳转等待 | 直接断言 URL 易失败 | 统一用 `ExpectedConditions.urlContains(...)` 显式等待 |
| **测试数据累积拖慢执行** | 多次执行后数据库累积 76 篇博客，列表页全量渲染导致 UI 测试从 53 秒涨到 325 秒（6 倍） | ① 提供清理脚本 `scripts/clean-test-data.sql`，跑测试前清理；② **根治：推动开发为列表接口实现分页（BUG-06 已修复）**，单页固定 10 条后渲染量恒定，上一次 32 条用例在 126 篇数据下也只需 80.4 秒 |

### 3.9 页面样式生效校验（1 条，2026-09 补充，回归 BUG-18）

> 背景：使用者反馈"列表页 UI 没了"——数据、文字都在，但卡片样式全部丢失，右栏退化成一片裸文字。
> 根因是浏览器缓存了旧 `list.css`（旧选择器 `.right > .blog` 匹配不到分页改造后多包一层的 `#blog-list`）。
> **原有 32 条用例全部通过却完全没发现这个问题**，因为它们只断言"元素存在 / 数量正确"。

| 编号 | 用例标题 | 预期结果 |
|---|---|---|
| UI-33 | 列表页样式表已生效，卡片样式未丢失 | `list.css` 已加载且规则可读；卡片 `getComputedStyle` 的背景非透明、内边距与圆角非 0 |

> 这条用例专门守住"元素在、页面却已经坏了"的盲区。**反向验证**：临时移除 `list.css` 后 UI-33 必定失败（`卡片样式未生效`），证明断言真的有效，而不是永远为真的摆设。

## 4. 执行方式与结果

```bash
# 前置：MySQL 已启动（连接配置见 src/test/resources/application-test.yml）
mvn test -Dtest=BlogUiTest
```

| 指标 | 结果 |
|---|---|
| 用例总数 | 33 |
| 通过 | **33（100%）** |
| 失败 | 0 |
| 执行耗时 | 80~92 秒（含 Spring 上下文启动 + 33 个页面流程）；**分页修复前**数据库累积大量测试数据时会显著变慢（实测 76 篇博客时劣化到 325 秒），见下方说明 |
| 截图证据 | 34 张，跑一次用例即在 `tests/evidence/ui/` 本地生成（该目录不入库，见 `.gitignore`） |
| 弹框文本证据 | `tests/evidence/ui/alert-evidence.md`（33 条实际弹框文本，同上，本地生成） |

首轮执行有 2 条失败（UI-13/UI-14，editor.md 内容写入时机问题），修正框架等待逻辑后**全部通过**——属于测试脚本问题，非产品缺陷。

### 执行耗时与数据量的关系（重要观察）

| 场景 | 数据库状态 | 执行耗时 |
|---|---|---|
| 首次执行 | 上架博客 0~10 篇 | 53.4 秒 |
| 多次执行后（分页前，23 条用例） | 上架博客 **76 篇**（测试数据累积） | **325 秒（6.5 倍）** |
| 执行清理脚本后（分页前） | 上架博客 0 篇 | **50.2 秒**（恢复） |
| **分页修复后（32 条用例，比原先多 9 条）** | 上架博客 **126 篇**（未清理数据直接跑） | **80.4 秒（基本不受数据量影响）** |
| **分页修复后 + 样式用例（33 条用例）** | 上架博客 **44 篇** | **91.7 秒** |

**原因**：列表页 `GET /blog/getList` 原先无分页、全量返回并全量渲染卡片，数据越多前端渲染越慢。这从测试侧实证了缺陷 **BUG-06（博客列表无分页）** 的性能风险，与 `docs/08-性能测试报告.md` 中"列表接口最慢"的结论相互印证。

**修复后**：接口按 `pageNum/pageSize` 分页（默认 10 条/页），前端只渲染当前页卡片，执行耗时不再随累计数据量增长。最终验证：数据库累积到 **126 篇**上架博客时，32 条用例仍只需 **80.4 秒**——用例数比原先多 9 条、数据量比原先多 50 篇，耗时反而从 325 秒回落到 80 秒级。

**处理**：提供清理脚本 `scripts/clean-test-data.sql`，按"字母前缀 + 数字后缀"识别测试账号并删除其账号与博客（真实账号不匹配该规则，不受影响）。脚本内置"先备份 → 先预览待删清单 → 再删除"三步，建议跑完自动化后执行一次。
> 配套改进：UI 用例生成的用户名后缀改为**固定 6 位**（`String.format("%06d", ...)`）。原先 `% 1000000` 得到 5794 这类 4 位后缀，会让清理规则的位数下界匹配不到，导致测试账号悄悄累积——生成端与清理端要一起对。
