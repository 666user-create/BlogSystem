# 08 性能测试报告（JMeter）

| 项目 | 内容 |
|---|---|
| 文档编号 | BS-TEST-DOC-08 |
| 被测系统 | BlogSystem 博客系统 v0.0.1 |
| 测试工具 | Apache JMeter 5.6.3（命令行模式）+ Java 23 / Maven |
| 测试计划 | `tests/perf/BlogSystem-性能测试计划.jmx` |
| 原始结果 | `tests/reports/jmeter/result.jtl`、`tests/reports/jmeter/index.html`（JMeter Dashboard）—— 本地生成，不入库 |
| 执行日期 | 2026-08 |

## 1. 测试目标与场景选择

博客系统的访问集中在三个高频接口，按"用户使用频率"选取压测场景：

| 序号 | 场景 | 接口 | 选择理由 |
|---|---|---|---|
| 1 | 用户登录 | POST /user/login | 每次会话入口，高频且含密码校验（CPU 计算：MD5 加盐） |
| 2 | 博客列表 | GET /blog/getList | 首页加载必调，分页查询 + 作者信息拼装（原全量查询，即缺陷 BUG-06，已修复） |
| 3 | 博客详情 | GET /blog/getBlogDetail | 详情页必调，跨表/跨服务读取作者名 |

性能指标：**吞吐量（TPS）**、**平均响应时间**、**最大响应时间**、**错误率**。

## 2. 测试方案

```
Thread Group：5 并发线程，ramp-up 2 秒，循环 10 次
   ├── 01 POST /user/login        （JSON 断言 code=200；JSON 提取器取 token 供后续接口使用）
   ├── 02 GET  /blog/getList      （断言 code=200；提取首篇博客 id 供详情接口使用）
   └── 03 GET  /blog/getBlogDetail?blogId=${blogId}（断言 code=200）

监听器：Summary Report + 命令行 -e -o 生成 HTML Dashboard
```

- 三个请求串联为一个事务迭代，共 5 线程 × 10 轮 = **150 个请求**
- 接口依赖通过 JSON 提取器（`$.data.token`、`$.data.list[0].id`）串联，模拟真实用户链路
- 每个请求都带响应断言（不只看 HTTP 状态码，还校验业务码 `code=200`）

## 3. 测试环境

| 项 | 配置 |
|---|---|
| 被测应用 | Spring Boot 3.3.5，内嵌 Tomcat，端口 8080（dev profile） |
| 数据库 | MySQL 8（本机），`java_blog_spring` |
| 压测机 | 与被测应用同机（Windows 10/11，JDK 23） |
| JVM | 默认启动参数（未做调优） |

> 说明：压测机与应用同机，结果不含网络传输损耗，反映的是应用自身处理能力。

## 4. 测试结果

### 4.1 整体结果

| 指标 | 结果 |
|---|---|
| 总请求数 | 150 |
| 持续时长 | 1.66 秒 |
| **吞吐量** | **90.1 请求/秒** |
| **平均响应时间** | **5.9 ms** |
| 最小 / 最大响应时间 | 3 ms / 42 ms |
| **错误率** | **0.00%** |

### 4.2 分接口结果

| 接口 | 请求数 | 平均响应(ms) | 最小(ms) | 最大(ms) | 错误数 |
|---|---|---|---|---|---|
| 用户登录 POST /user/login | 50 | 5.3 | 3 | 42 | 0 |
| 博客列表 GET /blog/getList | 50 | 7.4 | 5 | 9 | 0 |
| 博客详情 GET /blog/getBlogDetail | 50 | 5.0 | 3 | 7 | 0 |

### 4.3 结果分析

1. **整体响应优秀**：平均 5.9ms，远低于常见接口 SLA（200ms），错误率 0%，说明在当前数据量（数十篇博客）下应用处理能力充足；
2. **博客列表仍是三者中最慢（7.4ms）**：列表接口需做 `selectPage` 分页查询 + DO→Response 转换 + 作者信息拼装，工作量本身就大于详情接口，属合理范围；但**最大响应时间已从分页前的 14ms 收敛到 9ms**，不再随数据量线性增长；
3. **登录接口最大耗时 42ms**：为首次请求的类加载/JIT 预热（1 个请求 42ms，其余均在 3~6ms），属正常现象，非性能缺陷；
4. **详情接口稳定（3~7ms）**：依赖 `getAuthorInfo` 读取作者信息，未出现明显抖动。

### 4.4 分页改造（BUG-06）前后的实测对比

**（1）UI 自动化执行耗时**——数据量增长曾把端到端用例拖慢 6.5 倍：

| 数据库上架博客数 | UI 测试执行耗时 | 说明 |
|---|---|---|
| 0~10 篇 | 53.4 秒 / 50.2 秒 | 正常水平 |
| **76 篇（分页前，23 条用例）** | **325 秒** | 慢 6.5 倍，无分页导致列表页渲染全部 76 张卡片 |

原因链路：`GET /blog/getList` 无分页全量返回 → 响应体变大 → 前端循环拼接并渲染全部卡片 → 每个 UI 用例都要等列表页加载完成。这从"端到端体验"角度印证了 4.3 中"列表接口是首要瓶颈点"的判断，也说明 **BUG-06 不只是接口耗时问题，还会放大为页面级的性能问题**。

**（2）改造后验证**——BUG-06 已修复（详见缺陷清单），修复后重新压测与回归：

| 对比项 | 分页前 | 分页后 |
|---|---|---|
| 列表接口 平均响应 | 7.3 ms | 7.4 ms（基本持平） |
| 列表接口 **最大**响应 | 14 ms | **9 ms（收敛）** |
| 整体吞吐量 | 88 请求/秒 | **90.1 请求/秒** |
| UI 用例数 | 23 条 | 33 条（新增分页/权限/数据正确性/样式生效用例） |
| UI 用例执行耗时 | 76 篇数据下 325 秒 | **百篇级数据下 80~92 秒** |

分页把单次响应限制为固定 10 条，响应体大小不再随数据量增长，页面渲染量恒定——这就是 76 篇/325 秒 回落到百篇级/80~92 秒 的根本原因：**数据量翻了近一倍，用例数多了 10 条，耗时反而降到原来的 1/4**。

> 数据隔离脚本：`scripts/clean-test-data.sql`（仅按测试账号命名规则清理，保留真实账号数据）。

## 5. 结论与建议

**结论**：分页改造（BUG-06）完成后，当前版本在 5 并发场景下性能表现良好（吞吐量 **90.1 请求/秒**、平均 **5.9ms**、错误率 0），且列表接口响应不再随数据量增长而劣化，无性能阻塞问题。

**建议**：
1. **继续验证更大数据量**：分页已解决"全量返回"问题，建议把博客造数到千级/万级后重新压测，确认 `count(*)` 与深分页（如第 100 页）的开销是否可接受，必要时优化为游标分页（`lastId`）；
2. **补充更高并发场景**：本次为 5 并发基准测试，建议追加 20/50 并发阶梯压测，找出拐点与 TPS 上限；
3. **关注登录接口 CPU 开销**：密码为 MD5 加盐单轮计算，若后续提升为 BCrypt 等强哈希算法，需重新评估登录接口性能；
4. **引入持续性能测试**：可把本 `.jmx` 计划接入 CI 定时执行，监控接口性能回归。

## 6. 复现方式

```bash
# 1. 启动被测应用
mvn spring-boot:run -Dspring-boot.run.profiles=dev

# 2. 执行压测（命令行模式，自动生成 HTML 报告）
#    -o 要求目录不存在/为空，-l 要求文件不存在，所以先清掉上次产物
jmeter -n -t tests/perf/BlogSystem-性能测试计划.jmx -l tests/reports/jmeter/result.jtl -e -o tests/reports/jmeter

# 3. 查看报告
#    打开 tests/reports/jmeter/index.html
```

可覆盖参数：`-Jhost=127.0.0.1 -Jport=8080 -JuserName=admin -Jpassword=admin123`
