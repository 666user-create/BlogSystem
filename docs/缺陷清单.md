## 缺陷详情

### BUG-01：前端请求头 token 变量名与后端不一致，导致鉴权失败

- **严重级别**：高（功能完全不可用）
- **模块**：登录 / 鉴权
- **发现方式**：开发自测（登录后所有接口 401）
- **问题描述**：前端存储/发送的 token 请求头名与后端读取的请求头名不一致（`userToken` vs `user_token`），导致登录成功后携带的 token 后端读不到，所有受保护接口鉴权失败。
- **修复方式（分两步）**：
  - **第一步（临时兜底）**：前后端双兼容——前端登录成功后同时存储 `user_token` 与 `userToken` 两个键、请求时同时发送两个请求头；后端 `Constants.TOKEN_OLD = "userToken"` 兼容读取。保证新旧代码任意组合都能鉴权成功。
  - **第二步（最终方案，2026-09）**：统一字段名为 `user_token`，删除全部兼容层——
    - 前端 `blog_login.html` 只存 `user_token`；`common.js` 只读 `user_token`、只发一个请求头；
    - 后端删除 `Constants.TOKEN_OLD`，`LoginInterceptor` / `BlogController` 只读 `Constants.TOKEN`。
  - 之所以先兼容再统一：当时前后端分别部署，直接改字段名会让旧版本立即失效；兼容期结束后再收敛为标准方案。
- **回归验证**：登录后调用 `/blog/getList`、`/blog/add` 等接口不再 401；统一字段名后重跑 UI 自动化用例全部通过。
- **教训**：前后端字段名约定应统一并沉淀为常量/文档；出现不一致时先做兼容兜底保证可用，再择机统一（本缺陷的处置过程即是如此）。

### BUG-02：写博客入口未鉴权，未登录即可进入编辑页并发表

- **严重级别**：高（越权）
- **模块**：博客 / 鉴权
- **发现方式**：开发自测（未登录状态可进入写博客页并提交）
- **问题描述**：写博客入口（导航栏"写博客"按钮）在未登录时可见可点，未登录用户可进入编辑页并尝试发表博客。
- **修复方式**：以后端强制鉴权为准——
  - 后端 `LoginInterceptor` 拦截 `/blog/**`（含 `/blog/add`、`/blog/update`、`/blog/delete`），无 token 或 token 无效返回 401；
  - 前端 `common.js` 全局 `ajaxError` 兜底：收到 401 时清空登录态并跳转登录页。
- **现状说明**：未登录时前端"写博客"按钮仍显示（未做显隐控制），点击进入编辑页后发表请求会被后端 401 拦截并跳转登录页。建议后续按登录态控制入口按钮显隐，提升体验。
- **回归验证**：未登录调用 `/blog/add` 返回 401；登录后可正常发表。

### BUG-03：错误响应缺少业务错误码，用户看不懂

- **严重级别**：中（体验）
- **模块**：公共响应
- **发现方式**：开发自测（接口报错时前端仅弹出原始中文文案）
- **问题描述**：业务错误统一返回 `code = -1` + 中文 errMsg，没有细分业务错误码；前端无法按错误类型做差异化处理，用户看到的是"看不懂"的原始信息。
- **修复方式（部分）**：定义 `ResultCodeEnum`（`SUCCESS(200)` / `FAIL(-1)`）作为错误码枚举。
- **现状说明**：⚠️ 枚举已定义但**未接入实际返回逻辑**——`ExceptionAdvice` 与 `Result.fail()` 仍返回固定 `code=-1` + errMsg 字符串；前端仅按 HTTP 状态码（401/403/500）区分处理。建议后续：
  1. `Result` 携带业务错误码（如 `USER_NOT_FOUND`、`PASSWORD_ERROR` 等细分码）；
  2. 前端按业务错误码统一提示，而不是依赖中文文案匹配。

### BUG-04：密码明文与密码哈希写入日志

- **严重级别**：严重（敏感信息泄露）
- **模块**：登录
- **发现方式**：代码审查（`UserServiceImpl.checkPassWord`）
- **问题描述**：登录失败时日志打印用户输入的**明文密码**和数据库中的**密码哈希**：
  ```java
  log.info("数据库存储的密码: ... 完整值=[{}]", userInfo.getPassword());
  log.warn("密码验证失败: 输入=[{}], 数据库值=[{}]", request.getPassword(), userInfo.getPassword());
  ```
- **修复方式**：删除敏感日志，仅记录用户名：
  ```java
  log.warn("用户 {} 密码验证失败", request.getUserName());
  ```
- **修复提交**：`f3adba4 fix: 登录日志脱敏，避免密码明文与哈希写入日志`
- **回归验证**：密码错误时日志仅包含用户名，不含任何密码信息。

### BUG-05：JWT 密钥硬编码在源码中

- **严重级别**：严重（安全）
- **模块**：鉴权
- **发现方式**：代码审查（`JwtUtils`）
- **问题描述**：JWT 签名密钥为 `public static` 硬编码字段，任何拿到源码的人都能伪造任意用户（含 admin）的 token。
- **修复方式**：密钥配置化——
  - `JwtUtils` 密钥字段私有化，提供 `init(secret, expiration)`；
  - 新增 `JwtConfig`，启动时从 `application.yml` 注入；
  - 配置支持环境变量覆盖：`blog.jwt.secret: ${BLOG_JWT_SECRET:默认值}`。
- **修复提交**：`50fab90 fix: JWT 密钥配置化，支持环境变量 BLOG_JWT_SECRET 覆盖`
- **回归验证**：默认配置下登录签发/校验 token 正常；通过环境变量覆盖密钥后旧 token 失效（符合预期）。

### BUG-06：博客列表接口无分页，数据量大时全量查询

- **严重级别**：中（性能）
- **模块**：博客列表
- **发现方式**：代码审查（`BlogServiceImpl.getList`）
- **问题描述**：`/blog/getList`、`/blog/adminList` 一次性返回全部未删除博客，无分页参数，数据量增长后响应变慢、前端渲染卡顿。
- **实测证据**：数据库上架博客累积到 76 篇时，UI 自动化测试（23 条）执行耗时从 **50 秒劣化到 325 秒（6.5 倍）**——列表接口全量返回 + 前端全量渲染卡片导致每个页面用例都要等待列表加载。这证明该缺陷不仅是接口耗时问题，还会放大为页面级性能问题。
- **状态**：**已修复（2026-09）**
- **修复方案**：
  - **后端**：新增统一分页响应体 `PageResult<T>`（`{list, total, pageNum, pageSize, pages}`）；`/blog/getList`、`/blog/adminList` 支持 `pageNum`/`pageSize`（默认 1/10，pageSize 上限 50），非法参数返回 400；新增 `MybatisPlusConfig` 注册 `PaginationInnerInterceptor`（**不注册该插件 `selectPage` 不会真正分页**，这是实现分页最容易踩的坑）。
  - **前端**：列表页与管理员页改为渲染 `data.list`，并新增翻页控件（"共 N 篇 · 第 X/Y 页" + 上一页/下一页，首页/末页按钮自动禁用，只有一页时隐藏控件）；翻页控件与卡片区分离，避免刷新列表时把控件一起清空。
  - **边界处理**：页码越界返回空列表但 `total` 仍准确；无数据显示"暂无博客"，越界页显示"这一页没有内容了，请返回上一页"；管理页上下架切换后刷新当前页（保留页码）。
- **补测试**：
  - 单元测试 4 条：当前页转换、空数据、总页数向上取整（25 条/10 = 3 页）、越界页码 total 仍准确；
  - 接口自动化（pytest）5 条：pageSize 生效、越界返回空、参数非法 400、默认值、翻页不重不漏；
  - UI 自动化 2 条：多页时显示翻页控件且首页禁用"上一页"、点击下一页后数据变化并能返回。
- **回归验证**：接口自动化 45 条 + UI 自动化全部通过（当时 32 条，现已扩充至 33 条，另有开发侧单元测试 16 条）。
- **收益**：UI 自动化测试不再随数据量累积而显著变慢；列表接口最大响应时间从 14ms 收敛到 9ms。

### BUG-07：游客无法查看博客列表/详情（接口返回 401）

- **严重级别**：中（功能/体验）
- **模块**：鉴权 / 博客
- **发现方式**：接口测试（未带 token 调用 `/blog/getList`）
- **问题描述**：`LoginInterceptor` 拦截 `/blog/**`，导致**未登录游客**访问博客列表、博客详情等公开内容接口也返回 401。博客系统通常允许游客浏览，仅发表/编辑/删除需要登录。
- **处理决定**：保留。可作为需求争议点（产品定位：是否允许游客浏览）与缺陷记录。
- **建议**：拦截器按接口细分放行规则（如 `/blog/getList`、`/blog/getBlogDetail` 放行，写操作拦截）。

### BUG-08：登录接口无频率限制，存在暴力破解风险

- **严重级别**：中（安全）
- **模块**：登录
- **发现方式**：代码审查 / 安全测试（`/user/login` 无任何限流）
- **问题描述**：登录接口无失败次数限制、无验证码、无 IP 维度限流，可对弱口令账号进行暴力破解。
- **处理决定**：保留。作为测试报告"遗留风险"项；后续可引入简单限流（如固定窗口计数）或验证码。

### BUG-09：getUserInfo 可按任意 userId 查询他人信息

- **严重级别**：低（越权 / 信息暴露）
- **模块**：用户
- **发现方式**：接口测试（传入任意存在的 userId 均可返回用户信息）
- **问题描述**：`/user/getUserInfo` 未校验查询者身份与目标用户的关系，登录用户可查询任意 userId 的 github 主页、博客数量等信息。
- **处理决定**：保留。当前系统设计上该接口用于展示作者信息，泄露面有限；但建议后续明确"公开信息"与"私有信息"边界。

### BUG-10：管理员权限基于 token 中的用户名判断，而非数据库角色

- **严重级别**：中（权限模型脆弱）
- **模块**：权限
- **发现方式**：代码审查（`BlogController.checkAdmin`）
- **问题描述**：管理员校验为 `"admin".equals(JwtUtils.getUserNameFromToken(token))`——依赖 token 中的用户名 claim 字符串比较，而非数据库角色字段。虽然伪造需密钥，但权限模型不健壮（改用户名即改权限）。
- **处理决定**：保留。与 BUG-05 修复（密钥配置化）配合后伪造难度提高；建议后续引入角色字段（如 `role`），基于数据库校验。
- **建议**：`user_info` 表增加 `role` 字段，登录时写入 token，权限判断读取角色而非用户名。

### BUG-11：博客内容未做 XSS 过滤

- **严重级别**：中（安全）
- **模块**：博客
- **发现方式**：安全测试（Markdown 内容可包含原始 HTML/脚本）
- **问题描述**：博客 `content` 为 Markdown 原文存储，前端渲染时未做 XSS 过滤，用户可在内容中注入 HTML/脚本，存在存储型 XSS 风险。
- **处理决定**：保留。当前为个人使用场景，风险可控；建议后续在服务端/前端对内容做转义或白名单过滤。

### BUG-12：参数校验异常（@RequestParam 约束）未统一返回 400

- **严重级别**：中（接口契约不一致）
- **模块**：公共响应 / 参数校验
- **发现方式**：接口自动化测试——执行用例 TC-DET-04（`blogId=0` 期望 400）时发现实际返回 200
- **问题描述**：Controller 类标注 `@Validated` 后，`@RequestParam` 上的约束校验（如 `@Min(1)`）由 MethodValidationInterceptor 执行，校验失败抛出 `ConstraintViolationException`；而 `ExceptionAdvice` 未处理该异常，被最宽泛的 `Exception` handler 兜住，返回 HTTP 200 + `errMsg`，与 body 参数校验失败返回 400 的行为不一致。
- **影响**：前端无法通过 HTTP 状态码区分"参数不合法"与"业务失败"，接口契约不一致。
- **修复方式**：`ExceptionAdvice` 增加 `ConstraintViolationException` 的 `@ExceptionHandler`，统一返回 HTTP 400 + "参数校验失败"。
- **修复提交**：`59b95e3 fix: 参数校验异常统一返回400（补充 ConstraintViolationException 处理）`
- **回归验证**：`getBlogDetail?blogId=0` 返回 400（TC-DET-04 通过）。

### BUG-13：列表页引用不存在的图片，每次加载产生 404 请求

- **严重级别**：低（前端资源引用错误）
- **模块**：前端静态页
- **发现方式**：手工探索（浏览器 F12 → Network 面板发现 `GET /tuiao.png` 返回 404）
- **问题描述**：`blog_list.html` 导航栏 logo 引用了 `tuiao.png`，但该文件并不存在（`static/` 下只有 `pic/logo2.jpg`、`pic/site-bg.png`）。虽然 `<img>` 标签写了 `onerror` 兜底换成 `pic/logo2.jpg`（图标最终能显示），但每次打开页面都会产生一次无效的 404 请求，控制台报警告。
- **影响**：不影响功能，但产生无效请求、干扰控制台排查（真出问题时容易被这类噪音掩盖）。
- **修复方式**：`src` 直接指向真实存在的 `pic/logo2.jpg`，并移除不再需要的 `onerror` 兜底；同时用脚本全量扫描所有页面的 `src/href` 引用，确认无其他断链（扫描结果：0 处）。
- **回归验证**：重启后刷新列表页，Network 面板不再出现 `tuiao.png` 请求；全站资源引用检查 0 断链。

### BUG-14：编辑页无法回显原博客内容，直接提交会覆盖原文

- **严重级别**：高（**存在数据丢失风险**）
- **模块**：前端页面 / 博客编辑
- **发现方式**：手工探索（从详情页点"编辑"进入 `blog_update.html`，发现编辑框显示的是默认占位文本，而非原博客内容）
- **问题描述**：`blog_update.html` 在脚本末尾**立即**调用 `getBlogInfo()`，而 editor.md 编辑器是在 jQuery ready 回调中**异步**初始化的。AJAX 返回数据时 `window.editor` 往往尚未就绪，代码走了 `else` 分支，把内容写进了**隐藏的 textarea**（`#content`，`display:none`），编辑器里仍然显示默认占位文本 `##在这里写下一篇博客`。
  - 现象：页面"看似正常"（编辑器正常渲染、标题也填上了），但正文不是原文；
  - 风险：用户若不核对内容直接点"更新文章"，**原博客正文会被这句占位文本覆盖**，造成内容丢失。
- **修复方式**：
  - `blog_update.html`：改用 editor.md 的 `onload` 回调，在编辑器（含底层 CodeMirror）**完全加载后**再调用 `getBlogInfo()` 回显内容；移除脚本末尾的立即调用；
  - `blog_edit.html`：同样把 `window.editor` 的赋值移入 `onload`，避免过早提交时 `getMarkdown()` 取不到内容；
  - **补测试**：UI-19 用例新增"编辑页正确回显原标题与原文内容"断言（原用例用 JS 直接写入内容后提交，绕过了回显逻辑，因此漏掉了该缺陷）。
- **回归验证**：UI-19 断言编辑页标题与正文均回显为原文，UI 自动化用例全部通过。
- **教训**：涉及异步初始化组件（编辑器、图表等）的页面，回显数据的时机必须绑定组件就绪回调；测试用例也要覆盖"数据回显"而不只是"提交成功"，否则会漏掉这类"看着正常实则拿不到数据"的缺陷。

### BUG-15：详情页未渲染 Markdown，语法原样显示

- **严重级别**：中（内容展示错误）
- **模块**：前端页面 / 博客详情
- **发现方式**：代码审查 + 新增 UI 用例验证（UI-24）
- **问题描述**：`blog_detail.html` 用 `$(".content .detail").text(result.data.content)` 直接塞纯文本，Markdown 语法（`## 标题`、`**加粗**`、代码块、列表等）会**原样显示**，读者看到的是源码而不是排版后的文章。页面明明引入了 `marked.min.js`、`prettify.min.js`（本意是要渲染的），却从未调用。
- **影响**：博客的核心价值就是文章排版，Markdown 不渲染等于详情页展示错误内容。
- **修复方式**：改用 marked 把 Markdown 渲染为 HTML——兼容 editor.md 自带旧版（`marked(src)` 函数式）与新版（`marked.parse(src)`），两者都不可用时兜底为转义后的纯文本，避免出现空白页。
- **补测试**：新增 UI-24「详情页正确渲染 Markdown」，断言正文容器的 innerHTML 中出现 `<h2>`/`<strong>` 标签（而不是原始 `**` 符号）。
- **回归验证**：UI-24 通过；修复前该用例失败（innerHTML 为 `**加粗文本**`），修复后渲染为 `<strong>`。

### BUG-17：详情页未按作者身份控制"编辑/删除"按钮显隐

- **严重级别**：低（UI 权限控制缺失；后端已有校验兜底，不构成安全漏洞）
- **模块**：前端页面 / 博客详情
- **发现方式**：需求走查（"不是作者就不应该显示编辑和删除的 UI"）
- **问题描述**：详情页的"编辑/删除"按钮对**所有登录用户**都显示。非作者点击后才会被后端拒绝（`无权编辑该博客` / `无权删除该博客`），属于"先给操作入口、再报错"的糟糕交互，也不符合最小权限的界面规范。
- **修复方式**：
  - 详情页新增作者判断：`sessionStorage.loginUserId === blog.userId` 时才显示操作按钮；
  - 按钮区域默认 `display:none`（即使 JS 未执行也不会误显示），由 JS 判断身份后 `show()`；
  - 完善作者展示：正文区新增"作者：xxx"；**左侧卡片改为展示当前登录用户**（与列表页保持一致，不再重复展示作者，文章计数 id 由 `author-blog-count` 改为 `user-blog-count`）；
  - 后端**保留**原有作者校验（前端隐藏只是体验优化，真正的权限边界仍在服务端）。
- **补测试**：UI-27（正文区展示作者名）、UI-28（作者本人可见编辑/删除按钮）、UI-29（**非作者不可见**编辑/删除按钮——用另一个账号打开同一篇博客验证）、UI-30（左侧卡片展示当前登录用户、正文展示作者）。
- **回归验证**：33 条 UI 用例全部通过。

### BUG-18：前端静态资源没有版本号，新 HTML 配旧 CSS 导致页面样式整体失效

- **严重级别**：中（页面样式整体丢失，功能仍可用，但用户会直接认为"页面被改坏了"）
- **模块**：前端页面 / 静态资源缓存
- **发现方式**：使用者反馈 + 手工探索（浏览器仍在用缓存里的旧 `list.css`，列表页卡片样式全部消失，右栏退化成一片纯文本链接）
- **问题描述**：BUG-06 分页改造把博客卡片包进了新的 `#blog-list` 容器，`list.css` 的卡片选择器相应从 `.right > .blog`（直接子选择器）改成 `.right .blog`（后代选择器）。但浏览器的缓存里还是旧 `list.css`——旧选择器匹配不到新的 DOM 层级，于是卡片的背景、内边距、圆角、悬浮动效**全部失效**：数据都在、文字都在，但看起来"UI 没了"。
- **根因**：
  1. 静态资源引用不带版本号（`css/list.css` 没有 `?v=`），浏览器长期复用旧文件；
  2. 服务端没有给静态资源设置缓存校验策略，HTML 与 CSS 可能来自不同版本，出现"前端资源版本错配"。
- **修复方式**：
  1. 7 个业务页面（login / list / edit / update / detail / admin / register）对 `css/*.css` 与 `js/common.js` 的引用统一加版本参数 `?v=20260913`；以后改样式只要调版本号就能强制刷新。第三方库（jquery、editormd、marked）不加版本号，保持可缓存；
  2. `application.yml` 增加 `spring.web.resources.cache.cachecontrol.no-cache: true`：静态资源每次请求都做条件校验，未变更返回 304（开销可忽略），从机制上杜绝"新 HTML + 旧 CSS"。
- **补测试**：UI-33「列表页样式表已生效，卡片样式未丢失」——用 `getComputedStyle` 断言卡片背景非透明、内边距与圆角非 0，并断言 `list.css` 已加载且规则可读。
  - 这条用例专门补原有 UI 用例的盲区：**原来只断言"元素存在 / 数量正确"，一旦 CSS 失效，这些断言照样通过**，页面已经退化成裸文字却测不出来。
  - 反向验证：临时移除 `list.css` 后 UI-33 必然失败（`卡片样式未生效`），证明断言真的有效。
- **回归验证**：33 条 UI 用例全部通过；缺失样式场景下 UI-33 失败。
- **教训**：自动化断言不能只看"元素在不在"，还要看"样式/数据对不对"；前端资源发布必须带版本号，否则"改了前端但没生效"会长期困扰使用者。
