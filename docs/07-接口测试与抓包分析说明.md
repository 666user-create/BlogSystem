### 2.2 fixture 设计（避免用例间耦合）

| fixture | 作用 |
|---|---|
| `base_url`（session） | 读取 `BASE_URL` 环境变量，会话开始时做健康检查，服务未启动直接给出启动指引 |
| `new_user` | 注册随机用户名（前缀 + 时间戳），保证用例可重复执行 |
| `token` / `auth` | 新用户登录后的 token 与请求头 |
| `other_user` | **另一个独立用户**，专用于"非作者越权"用例（避免复用 auth 导致自己改自己） |
| `admin_headers` | 管理员登录态（admin/admin123） |

> 踩坑记录：最初越权用例直接复用了 `new_user`/`token`，导致"用户 B"其实就是作者本人，断言失败；抽出独立的 `other_user` fixture 后修复。

## 3. 抓包分析（Fiddler 场景的自动化实现）

### 3.1 为什么不用 Fiddler 直接跑

Fiddler 是 GUI 工具，抓包过程依赖人工操作，无法纳入自动化回归。

本工程用 **自建 HTTP 抓包代理**（`proxy_server.py`）实现同样的验证目标：

```
pytest 用例  →  本地抓包代理(127.0.0.1:8899)  →  被测应用(127.0.0.1:8080)
                        ↓
              记录请求行/请求头/请求体 → 落盘 JSON 证据
```

对应用例：
- **TC-SEC-05**：通过代理登录，断言抓包记录包含该请求，并输出请求明细；
- **TC-SEC-06**：断言响应头不含 `password/secret/token=/authorization` 等敏感字段，响应体不回显密码；
- **TC-SEC-02**：用户名传入 `' OR '1'='1`，断言不产生 500、不泄露 SQL 异常。

证据文件：`tests/evidence/capture/login-capture.json`（跑抓包用例时本地生成，不入库）

### 3.2 抓包结论（重要发现）

| 结论 | 说明 | 风险等级 |
|---|---|---|
| 登录请求**明文传输密码** | 抓包可见请求体 `{"userName":"...","password":"123456"}`；当前部署为 HTTP（8080），未启用 HTTPS | **中**（生产环境必须启用 HTTPS，否则明文密码可被链路窃听） |
| 响应头无敏感信息泄露 | 未发现密码/密钥类响应头 | 通过 |
| 密码不回显 | 登录响应仅返回 userId/token/userName | 通过 |
| SQL 注入不生效 | 注入串走正常业务判断（参数校验拦截或"用户不存在"），无 500、无堆栈泄露 | 通过 |

> 该结论与缺陷清单 BUG-08（登录无频率限制）同属"安全加固"建议项，已记录在 `docs/缺陷清单.md`。

## 4. Allure 报告

```bash
# 1) 跑用例（pytest 已配置 --alluredir=../reports/allure-results，在 tests/api-python 目录执行）
python -m pytest

# 2) 渲染 HTML 报告（需 allure 命令行）
allure generate ../reports/allure-results -o ../reports/allure-python --clean
allure open ../reports/allure-python
```

接口用例已用 `@allure.feature / @allure.story / @allure.title / @allure.severity / @allure.step` 标注，报告按"模块 → 用例"分组展示，并可附抓包明细等附件。
