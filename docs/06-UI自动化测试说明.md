## 1. 框架设计

```
src/test/java/org/example/blogsystem/ui/
└── BlogUiTest.java          # UI 自动化测试主类（23 条用例）

docs/test-evidence/ui/       # 截图证据（23 张，随用例执行自动生成）
```

| 设计要点 | 说明 |
|---|---|
| `@SpringBootTest(RANDOM_PORT)` | 测试自己启动应用并分配随机端口，无需手工启动 8080，可进 CI |
| `@ActiveProfiles("test")` | 使用独立测试数据库配置，与开发/生产隔离 |
| Headless Chrome | `--headless=new` 无界面运行，执行快、适合 CI |
| 显式等待（WebDriverWait） | 全部使用显式等待元素/URL/alert，不使用 `Thread.sleep`，降低偶发失败 |
| 截图断言 | 每用例关键步骤截图到 `docs/test-evidence/ui/`，并断言"文件生成且非空" |
| 弹框文本证据 | 原生 alert/confirm 无法被截图捕获（见第 2 节），额外产出 `alert-evidence.md` 文本证据 |
| 数据独立 | 每次注册随机用户名（前缀 + 时间戳），用例可重复执行、互不污染 |
| 登录态隔离 | `@BeforeEach` 回到登录页并 `sessionStorage.clear()`，保证用例从干净状态开始 |

## 2. 关键技术点与踩坑记录

| 问题 | 现象 | 解决方案 |
|---|---|---|
| editor.md 编辑器内容写入 | `window.editor.setMarkdown()` 报 `Cannot read properties of undefined (reading 'setValue')` | editor.md 异步挂载底层 CodeMirror，改为等待 `window.editor.cm.setValue` 就绪后直接调 `cm.setValue()` |
| 原生 alert 阻塞 | 登录失败/发表成功等提示为 `alert()`，不处理会阻塞后续操作 | 封装 `acceptAlert(scene)`：显式等待 `alertIsPresent()` → 取文本 → `accept()` |
| **原生弹框无法截图** | 截图里只有页面、看不到"究竟提示了什么"（alert 不属于页面 DOM） | 关闭弹窗后，用 JS 把**实际提示文本**绘制成右上角黄色浮层再截图；同时把文本累积落盘为 `alert-evidence.md` |
| 删除确认弹窗 | 删除博客前有 `confirm()` | 同样用 `acceptAlert()` 处理，再等待跳转回列表页 |
| 页面跳转等待 | 直接断言 URL 易失败 | 统一用 `ExpectedConditions.urlContains(...)` 显式等待 |
| **测试数据累积拖慢执行** | 多次执行后数据库累积 76 篇博客，列表页全量渲染导致 UI 测试从 53 秒涨到 325 秒（6 倍） | 提供清理脚本 `scripts/clean-test-data.sql`，跑测试前清理；该现象同时实证了缺陷 **BUG-06（列表无分页）** 的性能风险 |

## 4. 执行方式与结果

```bash
# 前置：MySQL 已启动（连接配置见 src/test/resources/application-test.yml）
mvn test -Dtest=BlogUiTest
```

| 指标 | 结果 |
|---|---|
| 用例总数 | 23 |
| 通过 | **23（100%）** |
| 失败 | 0 |
| 执行耗时 | 50.2 秒（含 Spring 上下文启动 + 23 个页面流程）；**数据库累积大量测试数据时会显著变慢**，见下方说明 |
| 截图证据 | 23 张，位于 `docs/test-evidence/ui/` |
| 弹框文本证据 | `docs/test-evidence/ui/alert-evidence.md`（33 条实际弹框文本） |

首轮执行有 2 条失败（UI-13/UI-14，editor.md 内容写入时机问题），修正框架等待逻辑后**全部通过**——属于测试脚本问题，非产品缺陷。

### 执行耗时与数据量的关系（重要观察）

| 场景 | 数据库状态 | 执行耗时 |
|---|---|---|
| 首次执行 | 上架博客 0~10 篇 | 53.4 秒 |
| 多次执行后 | 上架博客 **76 篇**（测试数据累积） | **325 秒（6.5 倍）** |
| 执行清理脚本后 | 上架博客 0 篇 | **50.2 秒**（恢复） |

**原因**：列表页 `GET /blog/getList` 无分页、全量返回并全量渲染卡片，数据越多前端渲染越慢。这从测试侧实证了缺陷 **BUG-06（博客列表无分页）** 的性能风险，与 `docs/08-性能测试报告.md` 中"列表接口最慢"的结论相互印证。

**处理**：提供清理脚本 `scripts/clean-test-data.sql`（逻辑删除非 admin 账号的博客），长期跑自动化前执行即可。
