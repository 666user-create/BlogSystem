## 缺陷详情

### BUG-01：前端请求头 token 变量名与后端不一致，导致鉴权失败

- **严重级别**：高（功能完全不可用）
- **模块**：登录 / 鉴权
- **发现方式**：开发自测（登录后所有接口 401）
- **问题描述**：前端存储/发送的 token 请求头名与后端读取的请求头名不一致（`userToken` vs `user_token`），导致登录成功后携带的 token 后端读不到，所有受保护接口鉴权失败。
- **修复方式**：前后端双兼容——
  - 前端登录成功后同时存储两个键：`blog_login.html` 中 `sessionStorage.setItem("user_token", ...)` 与 `setItem("userToken", ...)`；
  - 前端请求同时设置两个请求头：`common.js` 中 `xhr.setRequestHeader("user_token", ...)` 与 `setRequestHeader("userToken", ...)`；
  - 后端兼容读取两个头：`Constants.TOKEN = "user_token"`、`Constants.TOKEN_OLD = "userToken"`，`LoginInterceptor`/`BlogController` 优先读 `user_token`，缺失时兜底 `userToken`。
- **回归验证**：登录后调用 `/blog/getList`、`/blog/add` 等接口不再 401。
- **教训**：前后端字段名约定应统一并沉淀为文档/常量，避免联调踩坑。

### BUG-02：写博客入口未鉴权，未登录即可进入编辑页并发表

- **严重级别**：高（越权）
- **模块**：博客 / 鉴权
- **发现方式**：开发自测（未登录状态可进入写博客页并提交）
- **问题描述**：写博客入口（导航栏"写博客"按钮）在未登录时可见可点，未登录用户可进入编辑页并尝试发表博客。
- **修复方式**：以后端强制鉴权为准——
  - 后端 `LoginInterceptor` 拦截 `/blog/**`（含 `/blog/add`、`/blog/update`、`/blog/delete`），无 token 或 token 无效返回 401；
  - 前端 `common.js` 全局 `ajaxError` 兜底：收到 401 时清空登录态并跳转登录页。
- **现状说明**：未登录时前端"写博客"按钮仍显示（未做显隐控制），点击进入编辑页后发表请求会被后端 401 拦截并跳转登录页。建议后续按登录态控制入口按钮显隐，提升体验。
- **回归验证**：未登录调用 `/blog/add` 返回 401；登录后可正常发表。

### BUG-03：错误响应缺少业务错误码，用户看不懂

- **严重级别**：中（体验）
- **模块**：公共响应
- **发现方式**：开发自测（接口报错时前端仅弹出原始中文文案）
- **问题描述**：业务错误统一返回 `code = -1` + 中文 errMsg，没有细分业务错误码；前端无法按错误类型做差异化处理，用户看到的是"看不懂"的原始信息。
- **修复方式（部分）**：定义 `ResultCodeEnum`（`SUCCESS(200)` / `FAIL(-1)`）作为错误码枚举。
- **现状说明**：⚠️ 枚举已定义但**未接入实际返回逻辑**——`ExceptionAdvice` 与 `Result.fail()` 仍返回固定 `code=-1` + errMsg 字符串；前端仅按 HTTP 状态码（401/403/500）区分处理。建议后续：
  1. `Result` 携带业务错误码（如 `USER_NOT_FOUND`、`PASSWORD_ERROR` 等细分码）；
  2. 前端按业务错误码统一提示，而不是依赖中文文案匹配。

### BUG-04：密码明文与密码哈希写入日志

- **严重级别**：严重（敏感信息泄露）
- **模块**：登录
- **发现方式**：代码审查（`UserServiceImpl.checkPassWord`）
- **问题描述**：登录失败时日志打印用户输入的**明文密码**和数据库中的**密码哈希**：
  ```java
  log.info("数据库存储的密码: ... 完整值=[{}]", userInfo.getPassword());
  log.warn("密码验证失败: 输入=[{}], 数据库值=[{}]", request.getPassword(), userInfo.getPassword());
  ```
- **修复方式**：删除敏感日志，仅记录用户名：
  ```java
  log.warn("用户 {} 密码验证失败", request.getUserName());
  ```
- **修复提交**：`f3adba4 fix: 登录日志脱敏，避免密码明文与哈希写入日志`
- **回归验证**：密码错误时日志仅包含用户名，不含任何密码信息。

### BUG-05：JWT 密钥硬编码在源码中

- **严重级别**：严重（安全）
- **模块**：鉴权
- **发现方式**：代码审查（`JwtUtils`）
- **问题描述**：JWT 签名密钥为 `public static` 硬编码字段，任何拿到源码的人都能伪造任意用户（含 admin）的 token。
- **修复方式**：密钥配置化——
  - `JwtUtils` 密钥字段私有化，提供 `init(secret, expiration)`；
  - 新增 `JwtConfig`，启动时从 `application.yml` 注入；
  - 配置支持环境变量覆盖：`blog.jwt.secret: ${BLOG_JWT_SECRET:默认值}`。
- **修复提交**：`50fab90 fix: JWT 密钥配置化，支持环境变量 BLOG_JWT_SECRET 覆盖`
- **回归验证**：默认配置下登录签发/校验 token 正常；通过环境变量覆盖密钥后旧 token 失效（符合预期）。

### BUG-06：博客列表接口无分页，数据量大时全量查询

- **严重级别**：中（性能）
- **模块**：博客列表
- **发现方式**：代码审查（`BlogServiceImpl.getList`）
- **问题描述**：`/blog/getList`、`/blog/adminList` 一次性返回全部未删除博客，无分页参数，数据量增长后响应变慢、前端渲染卡顿。
- **处理决定**：保留。当前为个人学习项目，数据量小；可作为后续性能测试（JMeter 压测）与优化（分页/游标）的素材。
- **建议**：接口增加 `pageNum/pageSize` 参数，返回分页结构。

### BUG-07：游客无法查看博客列表/详情（接口返回 401）

- **严重级别**：中（功能/体验）
- **模块**：鉴权 / 博客
- **发现方式**：接口测试（未带 token 调用 `/blog/getList`）
- **问题描述**：`LoginInterceptor` 拦截 `/blog/**`，导致**未登录游客**访问博客列表、博客详情等公开内容接口也返回 401。博客系统通常允许游客浏览，仅发表/编辑/删除需要登录。
- **处理决定**：保留。可作为需求争议点（产品定位：是否允许游客浏览）与缺陷记录。
- **建议**：拦截器按接口细分放行规则（如 `/blog/getList`、`/blog/getBlogDetail` 放行，写操作拦截）。

### BUG-08：登录接口无频率限制，存在暴力破解风险

- **严重级别**：中（安全）
- **模块**：登录
- **发现方式**：代码审查 / 安全测试（`/user/login` 无任何限流）
- **问题描述**：登录接口无失败次数限制、无验证码、无 IP 维度限流，可对弱口令账号进行暴力破解。
- **处理决定**：保留。作为测试报告"遗留风险"项；后续可引入简单限流（如固定窗口计数）或验证码。

### BUG-09：getUserInfo 可按任意 userId 查询他人信息

- **严重级别**：低（越权 / 信息暴露）
- **模块**：用户
- **发现方式**：接口测试（传入任意存在的 userId 均可返回用户信息）
- **问题描述**：`/user/getUserInfo` 未校验查询者身份与目标用户的关系，登录用户可查询任意 userId 的 github 主页、博客数量等信息。
- **处理决定**：保留。当前系统设计上该接口用于展示作者信息，泄露面有限；但建议后续明确"公开信息"与"私有信息"边界。

### BUG-10：管理员权限基于 token 中的用户名判断，而非数据库角色

- **严重级别**：中（权限模型脆弱）
- **模块**：权限
- **发现方式**：代码审查（`BlogController.checkAdmin`）
- **问题描述**：管理员校验为 `"admin".equals(JwtUtils.getUserNameFromToken(token))`——依赖 token 中的用户名 claim 字符串比较，而非数据库角色字段。虽然伪造需密钥，但权限模型不健壮（改用户名即改权限）。
- **处理决定**：保留。与 BUG-05 修复（密钥配置化）配合后伪造难度提高；建议后续引入角色字段（如 `role`），基于数据库校验。
- **建议**：`user_info` 表增加 `role` 字段，登录时写入 token，权限判断读取角色而非用户名。

### BUG-11：博客内容未做 XSS 过滤

- **严重级别**：中（安全）
- **模块**：博客
- **发现方式**：安全测试（Markdown 内容可包含原始 HTML/脚本）
- **问题描述**：博客 `content` 为 Markdown 原文存储，前端渲染时未做 XSS 过滤，用户可在内容中注入 HTML/脚本，存在存储型 XSS 风险。
- **处理决定**：保留。当前为个人使用场景，风险可控；建议后续在服务端/前端对内容做转义或白名单过滤。
